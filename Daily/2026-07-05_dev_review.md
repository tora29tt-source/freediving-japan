# 開発状況レビュー（2026-07-05・fable5）

> 依頼：現状の客観レビューと今後の開発方針の意思決定材料。既存ドキュメントは書き換えず、本ファイルに提言をまとめる。

---

## 1. 現状評価サマリー

ドキュメントと実装の同期精度は個人開発として異例に高く、セキュリティ監査2巡・全件クローズ、ソフトデリート方針、RLS全テーブル整備まで運用が成熟している。一方で懸念は3点。

- **(a)** 7/2の「素潜り総合」転換がSTRATEGY止まりで、MEDIA_OPS・APP・ブランド名に波及していない
- **(b)** 7/4のショップ出品モデル（決済・RLSに触る全層変更）が未検証のまま次の作業が積まれるリスク
- **(c)** Phase 1のゴールだったiOSアプリが最も遅れているのに、実際の開発リソースはPhase 2領域（explore/media/トップ刷新）に流れており、ロードマップが実態を説明できていない

## 2. 全体整合性

**フェーズ定義が「順序」として機能していない。** DEV.mdの実装状況を見ると、Phase 2の中核（explore・media・トップ二層化・検索連携）がほぼ完成し、Phase 1の中核だったiOSアプリだけが🔄。「Webの勢いを優先した」合理的判断に見えるが、STRATEGYのフェーズは着手順ではなく**リリースゲート**（何が揃ったら公開するか）として再定義しないと意思決定の基準にならない。特に「アプリはPhase 1必須のままか、Phase 2以降に格下げするか」は明示的に決めるべき。

**APP.mdが2週間停滞（最終更新6/21）。** 実装状況表は「タブバー未着手・ログ画面未着手」のまま。DEV.mdの「開発中」と矛盾はしないが、アプリの現在地がどちらのドキュメントからも分からない。

**素潜り総合転換の下流未反映。** MEDIA_OPSはペルソナ5分類にシュノーケル単独層がなく、記事アイデア86本もほぼフリーダイビングKW。3ピラーの「入口最大化」を担うはずのシュノーケルSEO記事の設計が存在しない。APP.mdも旧ブランド前提。転換を本気でやるなら、メディアのカテゴリ・ペルソナ・記事リストの改訂が必要で、ブランド名決定と同時にやるのが二度手間を防ぐ。

**7/4モデル変更が設計書に未反映の可能性。** docs/INDEXでは EXPLORE / BOOKING / DB_SCHEMA 設計書が6/28更新のまま。instructor_shops N:M・shop_id nullable化は3書すべてに関わるので、「設計書同時更新ルール」に照らすと違反状態。

## 3. 技術的負債・セキュリティ残タスク（優先度順）

1. **【高】ショップ出品モデルの実機E2E未実施。** DB制約・RLS・RPC（`create_pending_booking` の shop_id 自動補完）・決済API・explore/pro/adminのUIまで触った変更が未検証。金銭フローに直結し、未検証のまま次の変更を積むとバグの切り分けが困難になる。リリース判断としては「これが通るまで explore/booking 系の新規開発は凍結」が妥当。テスト観点は最低3つ：①ショップ単体名義の出品→予約→決済 ②既存インストラクター名義の予約が回帰していないか ③instructor_shops 経由の所属表示。
2. **【高】セキュリティ修正の回帰E2E。** S1（予約INSERTのRPC一本化）・S3（articlesポリシー置換）・S6（TOCTOU）はChrome MCP確認済みだが、実ブラウザで「匿名予約→Stripe→Webhook→success.html」のフルフローと、editor/staff/adminの記事権限マトリクスを各1回通すべき。上記1と同一セッションで実施可能。
3. **【中】shopsのソフトデリート対象外。** 7/4以前は許容できたが、ショップが listings/bookings の親になった今、shops物理削除＝予約履歴の親を消す操作になりリスクが一段上がった。E2E完了後すぐ `deleted_at` + RESTRICTIVEポリシーを適用すべき（連鎖：shop → listings・slots）。
4. **【中】7/4変更の設計書反映**（EXPLORE / BOOKING / DB_SCHEMA / INDEX）。設計書が信頼できなくなると「Claudeが設計書を前提に書く」開発体制自体が劣化する。
5. **【低】`admin-mobile.html` 認証なし**（本番DBに触れない・Phase 2本番化時対応でOK）、ソフトデリート復元UI未実装（当面Supabase直接操作で許容）。
6. **【低】`docs/instructor/sales.md` / `manual.md`。** 技術負債ではなく営業資産。sales.mdはインストラクター獲得に直結するが、**ブランド名決定前に書くと書き直しになる**ため意図的にブランド決定後に置く。manual.mdは知見が溜まってからで問題ない。

## 4. リブランディング決定の進め方

**何をブロックしているか — 想定以上に広い。**

1. 独自ドメイン取得。MEDIA_OPS自身が「新ドメインのGoogle評価に3〜6ヶ月」と明記しており、この時計はドメイン確定まで動き出さない。vercel.appで記事を蓄積してから移行すると、リダイレクト管理と評価の希薄化コストを払う
2. iOSアプリ名（App Store申請）
3. SNSハンドル（@FreeJapan等）とプロフィールURL統一
4. プレスリリースの主語
5. learn講座・営業資料のブランド表記

つまり**Phase 2メディアローンチ準備とアプリ申請の両方の直前ブロッカー**であり、「記事ストック5本の制作開始前」が実質のデッドライン。

**決定プロセス提案：**

- **誰が**：Takuya単独決定（友人インストラクター数名への感触確認はプロセスに含める）
- **どう**：(1) 要件を先に固定 — 3ピラーを包含／日英で通じる／.jpまたは.com取得可／商標・既存サービスと衝突しない／App Store検索で埋もれない → (2) 候補3〜5案を出し、ドメイン・商標・SNSハンドルの空きを機械的にチェック（Claude/secretaryで1セッションで終わる作業） → (3) 数名に聞いて違和感チェック → (4) 決定し、STRATEGY改訂・ドメイン取得・SNS改名を同日に実行
- **いつまでに**：カレンダー期日より「メディア記事ストック制作の開始前」というマイルストーン依存で縛るのが実効的

**トレードオフと推奨：** 完全新ブランドは3ピラーを対等に見せられる反面、「Freediving Japan」と個人（日本記録保持者）に紐づいた認知・SNS資産を捨てる。据え置きはシュノーケル層への入口として名前が重い。**推奨は傘構造**：上位に素潜り総合の新ブランドを立て、「Freediving Japan」をフリーダイビング領域（ランキング・競技・learn）のサブブランドとして残す。既存資産を毀損せず、堀（競技の深さ）と入口（素潜りの広さ）を名前のレベルでも分離できる。

**戦略の両立性について1点。** 二層設計により「堀を薄めない」は構造上は成立している。ただしシュノーケル領域の勝敗はコンテンツではなく**在庫（体験商品の掲載数）**で決まる市場で、じゃらん・アソビュー等と正面衝突する。「入口はシュノーケルSEO・出口はフリーダイビング引き上げ」は未検証の仮説なので、シュノーケル向け投資（記事・出品獲得）は小さく張って転換率を計測してから広げる、という段階設計をSTRATEGYに一文入れることを勧める。
